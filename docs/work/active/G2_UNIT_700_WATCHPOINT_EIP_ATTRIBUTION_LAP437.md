# W18 — 슬롯3565 `+0x6f8..+0x700` write의 **EIP 귀속** (하드웨어 write watchpoint)

- 발행자 / 역할: lap437 Claude Code `claude-opus-5` / high / **middle(검수·중간계획)**.
  근거 `docs/history/laps/20260921_lap437_middle_g2_w18_card_issue.md`, `loop/ESCALATE_SOL` §24.
- 발행 권한: **strategy(lap436 §23 판정③)가 명시 허가한 1장**이다. 이 카드 외의 추가 진단
  카드는 허용되지 않는다. 이 카드의 결과는 **수리 카드** 또는 **strategy 중단판정**으로만 간다.
- 수행 역할: **work (Sonnet5/high)**. 실행 **1회 + 재시도 1회**, 총 **60분**.
- 목표 연결: G2 P2(원본 생산·AI 경로 안정성). fault `0x00414133` 인과 사슬의 **최상류 = 누가 쓰는가**.

## 1. 선행 확정 사항 (재조사 금지)

W10~W17 사슬이 닫은 것이며 이 카드는 **다시 재지 않는다**.

- **인과 사슬은 폐쇄형이다.** `K([+0x700]) → m([+0x68c]) → f688([+0x688])`, 산술
  `(10 + 347349) mod 65536 = 19679` 일치(lap425/426, lap434 재현).
- **(J2) 외부 write 확정.** 알려진 `+0x700` write 4곳(`0x40d733`/`0x40d79f`/`0x40f040`/
  `0x413120`) **전부 배제**(lap427 `src(+0x388)` 전 구간 0 + lap428 N41 `ebp` 논증 +
  lap431 네 site 명령 바이트 원본·후보 동일 확인 = 3중).
- **(L2) 단발형 확정(lap436 §23 판정①).** 전이 tick에 오염 오프셋(idx6/7/8)이 바뀐 슬롯은
  **3565 하나뿐**이고 그 축의 배경 변화율은 **0**이다 ⇒ **순회 루프 계열 소거.**
  lap437 middle이 원시 76행을 비참조 재계산해 **불일치 0**으로 재확인했다(§2).
- **정적 수단은 소진됐다.** P-L 7개 인코딩 0건, `rep movsd` 정적 후보 0건(N45),
  1200-bound 전방 순회는 `0x16F0B78`에 **사거리 미달**(N43, `0x43DF50` 위).
- **`+0x71c`(idx15)는 상시 카운터다.** 배경 diff 73행 중 49행이 여기서 나온다. 슬롯3604가
  전이 표본에 함께 뜨는 것은 **공오염이 아니다**(직전 표본 s342에도 변했다).

**(L2)의 정확한 사정거리(과대 인용 금지):** 소거된 것은 "**같은 오프셋**을 여러 슬롯에 쓰는
순회 루프"다. 잘못된 **stride**로 슬롯마다 다른 오프셋에 착지하는 루프는 이 측정으로 소거되지
않는다. 이 카드는 그 구분을 **EIP로 직접** 끝낸다.

## 3. 표적 — 단 하나

동일 fixture에서 **슬롯3565의 `+0x6f8` / `+0x6fc` / `+0x700`에 최초로 값을 바꾸는 store 명령의
EIP**를 잡는다. 값 해석·수리·새 가설은 이 카드의 일이 아니다.

### 3-A. 감시 주소 (lap437이 산출·검증, 변경 금지)

`POOL_BASE = 0x0108C000`, `UNIT_STRIDE = 0x758`, `slot = 3565`
⇒ `unit3565 = 0x0108C000 + 3565*0x758 = **0x016F0478**`

| 필드 | 선형 주소 | 정렬 |
|---|---|---|
| `+0x6f8` (idx6) | `0x016F0B70` | 4B 정렬 ✓ |
| `+0x6fc` (idx7) | `0x016F0B74` | 4B 정렬 ✓ |
| `+0x700` (idx8, `K`) | `0x016F0B78` | 4B 정렬 ✓ |

`0x016F0B78`은 lap428이 N43에서 독립적으로 낸 값과 **일치**한다(교차검증).
4B 정렬이므로 **x86 하드웨어 watchpoint 3개**로 정확히 덮인다(DR0~DR2, DR3 여유 1개).

### 3-B. 도구 — gdb 하드웨어 watchpoint (lap437이 환경에서 실증)

lap437이 격리된 throwaway 프로세스로 **이 호스트에서 실제로 확인**했다(게임 미실행):

- `/proc/sys/kernel/yama/ptrace_scope = **0**` ⇒ attach 가능.
- gdb 15.1이 `watch *(int*)<주소>`를 **`hw watchpoint`로 삽입**하고 old/new 값과 `$pc`를 보고한다.
- `set architecture i386` 지원 확인. 게임은 `PE32 … Intel 80386`.

**직접 ptrace `POKEUSER(u_debugreg)` 도구를 새로 쓰지 않는다** — 64bit tracer/32bit tracee의
`struct user` 레이아웃 문제와 스레드별 DR 전파를 직접 떠안게 된다. gdb는 inferior의 **모든
스레드**에 watchpoint를 전파하므로 그 두 문제를 대신 처리한다.

### 3-C. 실증된 함정 2건 — **반드시 반영** (lap437 스모크 테스트에서 실제로 발생)

1. **`$pc`는 store *다음* 명령을 가리킨다.** 실측: 트리거 `pc=0x401122`인데 실제 store는
   `0x40111c`(`mov %eax, …`)였다. 따라서 **보고할 EIP는 `$pc`가 아니라 그 직전 store 명령의
   주소**이며, 이를 혼동하면 엉뚱한 명령을 범인으로 지목한다.
2. **`x/Ni $pc-N` 역디스어셈블은 어긋난다.** 같은 실측에서 gdb가 `0x40111a`를
   `rex.RB clc`라는 **존재하지 않는 명령**으로 풀었다(명령 중간에서 시작한 탓).
   ⇒ 역추적은 gdb 출력에 의존하지 말고 **핀된 `candidate.bin`의 파일 오프셋
   `eip - 0x400000`에서 정방향 디스어셈블**해 명령 경계를 맞춘다(§4의 image base 규약).

## 4. 실행 순서 (이 순서를 바꾸지 않는다)

**Step 0 — 환경/주소공간 사전검증 (arm 전, 실패 시 즉시 (M5)).**
lap434 `movement_state_probe_pm.py`와 **동일한 검증된 game PID 발견 방식**으로 PID를 얻는다
(INBOX 2026-09-21 00:51 정정 준수 — 새 PID 추측 금지). 그 PID에 gdb attach 후:
- `x/2xb 0x400000` 이 `0x4d 0x5a`(`MZ`)여야 한다 ⇒ PE가 `0x400000`에 매핑됐고 gdb가 보는
  주소공간이 probe가 읽는 주소공간과 같음을 확인. 아니면 **(M5)**.
- `info inferiors` / `show architecture`로 32bit 컨텍스트를 기록한다. gdb가 64bit WoW64
  컨텍스트를 보고하면 `$eip`가 아닌 것을 읽을 위험이 있으므로 **그 사실을 기록하고 (M5) 판단**
  대상으로 올린다(즉석 우회 금지).
- `detach` 후 게임을 계속 진행시킨다.

**Step 1 — arm 시점까지 대기.** 슬롯3565가 **생존**하고 `+0x6f8/+0x6fc/+0x700`이 **아직 전부 0**
인 상태를 기존 probe 방식의 read로 확인한다(lap434 기준 spawn ≈ tick10233, 전이 ≈ tick10400).
`tick >= 10250` 이후에 arm하되 **전이 전**이어야 한다. arm 시점의 tick과 세 값을 기록한다.

**Step 2 — arm.** gdb attach 후 `set can-use-hw-watchpoints 1`,
`watch *(int*)0x016F0B70`, `watch *(int*)0x016F0B74`, `watch *(int*)0x016F0B78`.
`info watchpoints`가 세 개 전부 **`hw watchpoint`** 로 나와야 한다. 하나라도
`watchpoint`(소프트웨어)면 **즉시 (M5)** — 소프트웨어 watchpoint는 단일스텝이라 예산을 태운다.

**Step 3 — 실행·수집.** 트리거마다 **자동으로** 기록하고 continue 한다(사람 개입 없이):
`{trigger_seq, addr, old, new, pc, thread_id, wall_t}`. 게임은 계속 달려야 한다.
- **폭주 차단(사전 등록):** 트리거 누적 **200건**을 넘기면 즉시 중단하고 **(M5)** 로 보고한다
  (이 세 주소가 상시 write 대상이라는 뜻이며, 가설을 추가하지 않는다).

**Step 4 — 정지 조건.** `old == 0 and new != 0` 인 첫 트리거에서 정지하고 다음을 수집한다:
`$pc`, `$eip`, 전체 레지스터, `info threads`, `bt`(실패해도 무방·실패 사실을 기록),
그리고 **세 주소의 현재 값 전부**(한 명령이 셋을 다 썼는지, 세 번 따로 났는지 구분용).
그 뒤 `detach` 하고 게임을 종료한다. `STOP_TICK`은 **10500**(전이가 없으면 그때 종료).

**Step 5 — 정적 귀속.** §3-C(2)대로 핀된 `candidate.bin`에서 `eip - 0x400000` 주변을
**정방향** 디스어셈블해 범인 store 명령의 **주소·바이트·형태**를 확정하고, 같은 오프셋의
**원본** 바이트와 대조해 "후보가 새로 만든 코드인지 원본에도 있던 코드인지"를 기록한다.

## 5. 판정식 (실행 **전** 고정 — 실행 후 변경 금지, 갈래는 서로소)

`E` = Step 4에서 얻은 **범인 store 명령의 주소**(= `$pc`가 아니라 그 직전 store, §3-C(1)).

- **(M1) 귀속 성공 — `E`가 후보 `.text` 범위 안이다.** `0x401000 <= E < 0x4F9000`이고 Step 5에서
  그 오프셋이 실제 store 명령으로 풀린다. ⇒ **다음 카드는 수리 카드**(진단 아님).
  기록: `E`, 명령 바이트, 원본 대비 동일/상이, 스레드, 세 주소를 한 명령이 썼는지, 트리거 총수.
- **(M2) 트리거는 났으나 `E`가 후보 `.text` 밖이다.** (예: Wine/시스템 DLL, 힙, thunk)
  ⇒ **범인 계열이 "게임 코드"에서 "외부 모듈"로 바뀌는 결과이며 그 자체가 귀속 성과다.**
  `E`가 속한 매핑(`info proc mappings`의 모듈명·범위)을 기록하고 **보고 후 STOP**,
  **strategy 판정**으로 올린다. 여기서 새 진단을 이어붙이지 않는다.
- **(M3) 전이는 일어났는데 watchpoint가 안 터졌다.** Step 4의 폴링/사후 read로 세 값이
  `{17,16538,22432}`류로 바뀐 것이 확인되는데 트리거가 0건이다 ⇒ DR이 유지되지 않았거나
  (Wine의 컨텍스트 관리) 감시 밖 경로다. **동일 파라미터 1회 재시도** → 재현되면 `BLOCKED`.
- **(M4) 전이 비재현.** `STOP_TICK` 10500까지 세 값이 계속 0이다 ⇒ **동일 파라미터 1회
  재시도** → 두 번째도 실패하면 `BLOCKED`. 창 확대·파라미터 변경 금지.
- **(M5) 기술 불가.** Step 0/2 사전검증 실패, hw watchpoint 삽입 실패, 소프트웨어 폴백,
  트리거 200건 초과, attach 불가 중 하나 ⇒ **재시도 없이 즉시 `BLOCKED`**. 사유를 정확히 적는다.

`BLOCKED`(M3/M4/M5)와 (M2)는 전부 **strategy가 P2 귀속 트랙의 중단/전환을 판정**한다
(lap436 §23). work가 그 자리에서 다음 진단을 만들지 않는다.

**정직성 조항:** (M1)이 나와도 그것은 **"이 실행에서 이 주소를 쓴 명령"** 이다. 그 명령이
**왜** 그 주소를 계산했는지(포인터 출처)는 별개이며, 수리 카드가 다룬다. EIP 1개를
"근본 원인 확정"으로 승격해 쓰지 않는다.

**재발 방지 조항 이행(§23):** 위 판정식은 전체창 지표(§2 `B_full`/`|S_full|`)와 표적축 지표
(`B_triplet`/`|S_triplet|`)를 **둘 다 실행 전에 §2에 박아 두었고**, 이 카드의 성패 지표(`E`,
트리거 로그)도 실행 전에 고정했다. 실행 후 축 변경·재채점은 이 카드에서 **허용하지 않는다**
(lap436의 예외는 1회성이며 선례가 아니다).

## 7. 안전 (§23 안전 조항의 카드화)

- **계측 전용.** 게임 주소공간에 대한 **데이터 write 0건**이어야 한다.
  `WriteProcessMemory` / `process_vm_writev` / `PTRACE_POKEDATA` / `PTRACE_POKETEXT` **0건**.
  gdb 세션에서 `set var`, `print <대입>`, `jump`, `call`, `return`, `write`, `patch` **금지**.
  gdb 명령은 파일로 고정(`-x`)하고 그 파일을 산출물에 남겨 사후 검증 가능하게 한다.
- **디버그 레지스터 설정은 §23이 명시한 예외**다(CPU 레지스터이며 게임 메모리가 아니다).
  소프트웨어 watchpoint/브레이크포인트는 **게임 코드 바이트를 `0xCC`로 바꾸므로 금지**한다 —
  §5 (M5)가 소프트웨어 폴백을 즉시 BLOCKED로 두는 이유가 이것이다.
- 원본 실행/수정 금지, **직접 재해시**로 전후 불변 확인. `checks/safety.sh check` → `SAFETY_PASS`.
- **셸 background 금지.** 모델 세션이 동기로 기다린다(INBOX 2026-09-21 01:01 운영 규칙).
  "background 실행 중" 문구로 활성 프로세스를 주장하지 않고 PID/산출물 갱신을 확인한다.
