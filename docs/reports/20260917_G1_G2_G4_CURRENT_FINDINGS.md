## 1. G1 — 원본 구성1600×1200와 차후 고해상도 그림

### 1.1 요구와 서로 다른 두 결과

원본 기준은800×600/4:3다. 목표1600×1200에서는 UI·스프라이트·월드의 상대 크기와 구도,
조작을 유지해야 한다. 당장 그림 재제작은 요구하지 않지만, 나중에 2배 자산을 넣었을 때
그 세부 픽셀이800 최종 버퍼에서 사라졌다 다시 확대되는 구조는 합격이 아니다.

**A. 실제 렌더 버퍼를 넓히는 native 후보:** 원본 계열 패치에서 native 대화면 surface와 렌더 경로를
확인했다. native1600×1200/8bpp/pitch1600의PS3진입도관측했다. 그러나 stock 스프라이트/HUD의 원래 픽셀 크기와 넓어진 시야가 남아 원본 구도가 아니다.
원본 엔진이 대화면을 전혀 처리할 수 없다는 주장에는 반례지만, 사용자 목표 G1의 답은 아니다.

**B. 원본800 구도를 DxWrapper로1600 출력하는 후보:** 구도 프리뷰는 실제로 확인했다.
하지만 기존 저해상도 화면을 키우는 경로다. 이 설정만으로 고해상도 스프라이트 지원이 생기지 않는다.
DxWnd 같은 출력 확대와 사용자에게 보이는 효과가 비슷하다는 지적은 현재 프리뷰에 대해 타당하다.

### 1.2 실게임에서 확인한 프리뷰

동일 save000 장면을 원본/후보 별도 fresh 실행으로 대조했다.

| 항목 | 관측 | 해석 한계 |
|---|---|---|
| 로드 메뉴 | 원본을 최근접2배 후 후보1600 화면과1,920,000픽셀100% 일치, MAE0 | 해당 로드 메뉴 한 장면 |
| 게임 화면 | 최근접2배 원본과99.21313% 픽셀 일치, 채널MAE0.46984/255; 상단HUD 일치 | 별도 실행의 움직이는 요소가 있음. 전체 게임100% 동등성 아님 |
| 미니맵 | 동일 논리 입력 후 양쪽camera(39,53)→(49,159) | 해당 save 장면의 특정 클릭 |

화면이2배여도 자동 입력 주입은 원본 논리 좌표를 사용했다. 이것을 모든 물리 마우스/DPI/Windows
환경의 입력 검증으로 일반화하지 않는다. 생산·모든 메뉴·커서 겹침·정상 종료·장기 안정성도 별도다.

### 1.3 고해상도 교체 경로의 조사

작은 첫 목표로 실제 HUD 자원 SPR를 선정했다.

- 원본 호출: `43F250 → 419D80(10,3,0x24,0)`.
- ID0x24는 `fnt/resource.spr`; frame0은20×24, opaque315픽셀, indexed8-bit/RLE 자산.
- 방향: 배경 구도는 기존2배를 유지하고, 해당 자산의40×48 교체 세부를 **최종1600 출력에 직접** 합성.
- 원본 draw와 presentation의 같은 프레임 연결, palette·투명mask·clip·메뉴/커서 등 후속 가림 순서가 필요하다.
- 마지막에 임의 그림을 덧씌우는 방식이나 실제 SPR와 연결되지 않은 시험 그림은 성공으로 세지 않는다.

원본 자산 identity와 draw 인자는 정적으로 확인했다. 실제 최종 출력·프레임·합성 순서는 아직 닫지 못했다.

### 1.4 실게임 계측 실패를 정확히 구분

| 실행 | 실패 지점 | 실제 factory/device/Present 관측 |
|---|---|---:|
| 9/16 17:50 계열 | DLLattach 시점에DxWrapper 미로드 | 0 |
| 9/16 18:13 이후 계열 | 계측기의 잘못 전사한PE timestamp | 0 |
| 9/16 21:23 이후 교정 실행 | `preferred_image_base_mismatch` | 0 |

timestamp 오류는 실제 pinned 파일 값으로 고쳤다. 재배치된 코드 operand는 원본 PE의 HIGHLOW
세 항목에 근거해 검증했다. 최신 테스트는 production C verifier와 상수·테이블을 그대로 추출해
host GCC로 실행하고, preferred/relocated 주소와 오류 거부를 확인했다.

그럼에도 host 모형의 PE header/readability는 Wine 실제 로더 환경이 아니다. 마지막 게임에서는
DxWrapper가0x76FA0000에 로드됐지만 **실제 메모리 header의ImageBase 읽은 값은 로그에 없었다**.
따라서 검사 실패 원인은 미확정이다. 원본 렌더 한계가 확인된 실패가 아니라 계측의 식별 계약이 막힌 실패다.

Wine9.0 upstream에는 dynamic relocation 때 메모리 OptionalHeader.ImageBase를map_addr로 쓰는
조건부 경로가 있다. 현상 설명 후보이지만 Ubuntu 패키지/실제 해당 run의 메모리 값을 대신하지 않는다.
[Wine9.0 source](https://github.com/wine-mirror/wine/blob/wine-9.0/dlls/ntdll/unix/virtual.c#L2666-L2684).

### 1.5 현재 결론과 다음 판정 조건

- **되는 것:** 원본 구도를 키워 보여주는 프리뷰; 별도 native 대화면 렌더링.
- **안 된 것:** 실제 고해상도 교체 자산 세부를 보존한 실게임 출력. 교체 ON/OFF 성공 캡처는 없다.
- **판단:** 경로 자체의 불가능은 미입증. 요구대로 가능하다고도 아직 실증하지 못했다.
- 재개 시 첫 관문은 실제 로더 header 값·모듈 identity 계약을 확보한 제한 작업이다.
- 이어서 실제 단일 device/성공Present/같은generation1600×1200 backbuffer, 실제 SPR-frame 연결을 확보해야 한다.
- 최소 성공 증거는40×48 내부의 인접 출력 픽셀이 다른 세부, 대상 외 화면 불변, 메뉴/커서 가림과잔상 없음이다.
- 이 작은 성공도 월드 SPR·애니메이션·안개·그림자까지 지원한다는 증거는 아니다.

## 2. G2 — 활성8인 각각 전비5000 안정 플레이

### 2.1 실제5000은 한 owner에서 확인했다

초기 전비와 재계산 전비 두 코드 위치를 private EXE에서 fixed5000으로 바꾸는 패치는 확인했다.
실게임에서는142개의비용35유닛을 원본 함수로 시험 생성하고, HQ/일꾼을 포함해144객체/전비4990을 만들었다.
마지막 일꾼은 **정상 생산**으로 자원 차감·예약·완료를 거쳐145객체/전비5000이 됐다.
다음 생산 요청은 전비 부족으로 거부됐고, 저장된 pending 생산을 로드한 뒤 정상 완료도 확인했다.

시험 생성과 자원 지급이 있었다. 군대 전체를 정상 생산으로 만들었다는 주장은 하지 않는다.

마지막 load 이후24,836연속tick/약744초를 기록했다. 전투·생산이 계속되고 유닛 사망으로 사용 전비가
1070~5000 사이에서 변했다. 최대 군대를 전 구간 유지한 시험도,8명이 동시에5000인 시험도 아니다.
cap 필드8개가5000이어도 활성8인/5000 실군대의 증거가 아니다.

### 2.2 숫자를 올리는 것과 실제 수용량은 다르다

| 구조 | 확인값 | 영향 |
|---|---|---|
| 개인 객체 수 게이트 | 원본250, 일반 유닛8칸예약 규칙 | 전비가 남아도 count 경계에 먼저 도달할 수 있음 |
| 공유 UnitStruct 풀 |1200슬롯, slot0예약/할당1..1199, stride1880B | 플레이어 전부와 관련 객체가 공용 사용 |
| existence/age |각1200항목,2B | 본체만 늘려도 할당·재사용 자료 불일치 |
| active slot 목록 |1200항목,short | 끝 바로 뒤 count/live state 충돌 |
| 분류별 목록A/B |각1200항목,dword | 추가 객체가 count·후속state를 덮을 수 있음 |
| owner roster |4B slot목록과별도count | 개인 게이트와 저장/명령 처리도 함께 점검 필요 |

풀은 `[0x66B790,0x892410)`이다. 끝0x892410은 **다음 live bulk game-state의 시작**과 같다.
그래서 기존 자리에1201번째슬롯을 허용하는 것은 새 메모리를 확보하는 작업이 아니다.
현재 자료 구조대로라면 게임 상태를 덮을 주소를 만들므로 단순 상한 확장 실행은 금지했다.

### 2.3 용량 산술 — 메모리 초과와 구별

비용10객체로5000전비를 채우는 구성은 한owner500객체,8owner4000객체다.
slot0예약까지 고려하면 **이 구성 기준** 최소4001슬롯/7,521,880B≈7.17MiB의UnitStruct 본체가 필요하다.
건물·전비0객체·보조배열·효과·경로 데이터·전체게임 메모리를 포함한 최종 수용량은 아니다.

이 계산은 전체8인5000이32비트라서 메모리 총량만으로 불가능하다는 근거가 약함을 보여준다.
그러나 OOM 안전증명도 아니다. **현재 확정한 위험은 고정 풀 경계·인접 데이터 충돌**이며,
실제8인 최대군대의 OOM·tick시간·크래시는 아직 시험하지 않았다.

### 2.4 풀 재배치가 필요한 이유와 미완료

원본과 안 겹치는 별도arena에 본체와sidecar/목록을 옮기는 침습 패치를 검토했다.
하지만 기존 코드에는 풀 내부의 필드 주소·base/index displacement·별칭endpoint를 쓰는 참조가 많다.
raw 숫자·decoded operand 후보는 실제 reachable 참조와 같지 않아 일괄 치환할 수 없다.
현재manifest는core61기록을분류했지만1491후보기록은미분류이며전체coverage=INCOMPLETE/activation=NO-GO다.
1491은실제수정이필요한참조확정개수가아니라noise/간접참조를포함한미종결후보집계다.
특히0x892410은 pool-end이면서다른bulk-start,0x899A28은existence-end이면서age-base다.

저장/로드는1200기준existence를 순회하고 live1880B 레코드를 저장한다.
sidecar도기존bulk에 포함되어 있으므로 새 풀만 만들면 새slot이 정상 저장되는 것이 아니다.
구버전 save의명시적호환/거부, reset·재할당, 전체실제참조, ID/지원LAN 직렬화 계약은 미종결이다.
새arena가 실제게임에서4000live를 담은 실행 증거는 없다.

### 2.5 현재 결론과 구현 GO 조건

- **되는 것:** 한owner의진짜전비5000과일부저장/복원/생산,24k급연속simulation.
- **불가 판정 대상:** 전비상수·개인count만 바꿔서8인임의구성5000 안정성을 보장하는 방법.
- **전체목표 판단:** 침습 풀재배치의설계가능성은 있으나구현경로 미완성. 현재안전한제품패치 GO는 아니다.

- 실행 후: 활성8인, 저전비다수/혼합구성, 정상생산·전투·사망·재사용·저장복원·성능을 확인해야 한다.
- 지원LAN을 표시하려면 동기화/패킷/결정성의실제다중client 시험이 필요하다. 로컬AI8개로 대신하지 않는다.
- 16인제외는8인풀·저장문제를 해결하지 않는다. 다만 플레이어table/mask확장 부담은 이번제품범위에서 빠진다.

## 3. G4 — 길찾기와 자유대전 AI

### 3.1 길찾기 교체와 명령 발행 보완은 다른 일

원본A*관련entry/code를 정적으로 확인했다. **A*를 개선하거나 교체한 실게임 패치는 없다.**
고정장면·A*실소비충돌grid·고정출발/도착명령·tick별경로·원본반복동등성 fixture가 갖춰지지 않아
탐색상한/휴리스틱 숫자만 바꾸는 후보는 활성화하지 않았다.

후속고정seed AI시험이 있어도 장애물oracle/고정route/tick동등성까지 채웠다는 뜻은 아니다.
