최신 G9 관측기 수리판은 자식 프로세스 기록 누락을 고치고 새 게임 미실행 사전검사·집중 검사40개·독립 소스 검수를 통과했다. 짧게 실행되는 합성 보조 프로세스의 미확인 항목은 명시적으로 남겼다. 이어진 새 승인 실행은 Wine 9의 서버 경로 쓰기 거부로 다시 초기화 단계에서 실패했다. private 후보 EXE의 SHA와 소스 불변·소유 X 종료/회수는 확인했지만, 실제 G9 자리 배정이나 게임 멀티 통과는 아니다. 설치된 Wine의 경로 선택을 기준으로 최소 수리 방향을 재검토 중이다. G6·C0 정리 경로에는 독립 검수에서 종료된 프로세스의 회수 관련 추가 반례가 확인돼 보강 중이다.
후속 G9 경로는 새 prefix의 실제 inode로 서버 디렉터리 하나만 예약하도록 고쳐 집중 검사49개·독립 검수를 통과했다. 새 실제 실행에서 Wine 초기화는 성공했지만, 짧게 실행된 보조 프로세스의 출처를 확인하지 못해 게임 관측 전에 중단했다. C0 수리판은206개 검사가 통과했어도 독립 검수에서 회수 실패를 성공으로 판정하는 반례가 나와 반려했다. G6도 새 독립 검수 뒤 실제 실행했지만, 격리된 자식이 감독기의 프로세스 정보를 읽지 못해 Wine·게임·입력 전에 중단했다. 소스/입력8891개는 실행 후 재해시에서 불일치가 없었다. 실제 G6·G9 및 멀티 통과는 아직 아니다.
앞선 G9 r10 seed42 실행은 실제 게임에 진입하고 두 시점의 8개 자리 좌표 일치를 관측했지만, GDB 산술 오류로 함수 종료·완료된 복사 기록이 빠져 엄격한 검증에 실패했다. 이 실패 기록은 보존한다.
관측기 수리 뒤 **새 seed42·99 실행 모두 실제 PE의 동일 호출에서 진입→8개 선택 index→함수 종료→좌표 복사 완료** 기록을 확보했다. 두 실행 모두 index는 0–7 순서이고, 반환 좌표·복사 임시 배열·8개 자리 좌표가 일치했다. 명시된 8인 fixture로 시작했으며 시작 직후·정착 후 PS3 표본에서도 좌표 일치를 확인했다. 새 독립 검수는 원시 로그 재해석·10개 변조 음성대조·보호153073개 불변 확인 후 이 좁은 실제 사실만 수용했다. 원시 `/proc/maps` 재연 자료와 row-gap의 실행 전후 무변경 증거는 없으며, 캡처를 메모리 표본과 동일 시점이라는 증거로 쓰지 않는다. 원시 결과의 `LIVE_FAILED` 및 바깥 실행의 `HOLD_UNKNOWN_ORIGIN_AUDIT`·정리 UNKNOWN은 그대로 유지한다. 기존 지도·빈 자리·RNG/보조 함수 인과·멀티 검증이 남아 있어 G9 전체 합격은 아니다.
새 공식판 실행은 초기화 5단계·승인된 Return 1회·같은 PE의 타이틀 30.55초 생존을 확인했다. 다만 자체 관측기 등록과 최종 자식 회수에 미해결 항목이 남아 전체 정리·멀티 PASS는 아니다. 새 G6 실행도 첫 신원 확인 응답의 제한시간 초과로 Wine·게임·입력 전에 중단됐다. C0 R15 관측기와 G6 신원 채널의 새 소스 수리는 각각 독립 검수를 통과해 새 물리 경로를 준비 중이다. 이는 새 실행이나 과거 실패 원인 입증이 아니다. 멀티 관측기의 첫 화면 진입 전에 미래 세션 정보를 요구하는 순환 gate도 독립 반례로 확인해 별도 수리 중이며, 실제 두 플레이어의 방 생성·참가는 아직 확인하지 못했다.
후속 G6 새 실행에서는 감독기·컨트롤러의 두 신원 요청이 실제로 통과했다. 그러나 Wine 탐색기 시작 직후 셸 실행 단계(`/usr/bin/dash`)를 launcher 스크립트(`/usr/bin/wine-stable`)와 같은 실행 파일로 요구하는 관측기 검사에 걸려 게임 target·입력 전에 중단했다. 전체 결과는 UNKNOWN이며, 실제 실행 파일 전환을 정확한 소유 프로세스·핀으로 검증하도록 새 소스에서 수리 중이다. 제품 G6나 멀티의 합격·결함 판정은 아니다.
최신 공식 C0 실행은 초기화5단계·Return1회·같은 PE의 타이틀 약30초 관측과 소유 관측기 회수를 확인했다. 그러나 자체 Wine 프로세스8개를 private 보조 프로세스로도 중복 분류해 미확인 출처 의무가 남았다. 새 소스에서 정확한 Wine 소유권 분류를 수리 중이며, 원시 결과의 전체 정리 UNKNOWN과 멀티 미검증은 유지한다.
G6 실행 파일 전환 수리판은 새 독립 검수에서 반려됐다. 실행 전 승인 확인 순서, 전환 중 불완전한 프로세스 관측, 2초 제한 초과 수용의 세 반례를 재현해 새 복사본에서 수정 중이다. 검수 테스트의 출력 경로 누락으로 생긴 과거 소스 폴더의 canary 추가·디렉터리 메타데이터 변화도 이력에 공개하고 보존했다. 기존 소스 파일 해시 불변을 전체 폴더 불변으로 확대하지 않는다.
후속 독립 검수는 G6의 기존 세 반례 수리를 확인했지만, 실행 파일 경로와 해시 조회 사이의 추가 전환 경합으로 재반려했다(회귀71개·subtest15개 통과와 구분). C0 분류 수리판도 회귀295개는 통과했으나 실제 도구정보 경로의 신규 핀 누락과 불완전한 소유권 검사 때문에 반려됐다. 두 관측기를 새 소스에서 보강하며, 멀티 연결 코드의 생산자·소비자 계약 오류5건도 별도로 수정 중이다. 새 실제 실행·멀티 합격은 아직 없다.
G6의 실행파일 경로·해시를 같은 열린 파일에서 읽는 후속 수리는 새 독립 **소스 검수를 통과**했다(72개·subtest15개, 보호21337항목 불변). 그러나 새 격리 실행은 게임 실행 전 검사에서 테스트용 `chmod`·`/dev/null` 접근이 보호 규칙에 막혀 중단했다(72개 시도·오류6개, Wine·게임·입력0, 감독기·검사 자식 회수 확인). 보호 규칙을 유지한 테스트 자료 수리는 새 독립 소스 검수를 통과했다(실제 격리 CLI 72개·subtest15개, ABI8, 보호11409항목 불변). 과거 오류6개는 새 검사에서 모두 통과했으며, 보조 provenance와 출력 디렉터리를 포함한 새 물리 실행 경로를 준비 중이다. 이는 실제 G6 입력 합격이나 멀티 검증이 아니다. 멀티 공개 조회의 성공 결과에 `status`가 빠지던 결함은 새 소스에서 수정했다. 전체 생산자→공개 조회→입력 재검사 경로의 명시적 모의 검사를 확인했고, 고정 파일명 캡처의 기존 파일 덮어쓰기·삭제 위험도 새 자료 생성·정리 방식으로 고쳤다. 최신 독립 **소스 검수 통과**: 회귀46개·C0 회귀290개·적대 조건14개, 보호2449항목 불변. 이는 실제 화면·네트워크 검증이 아니며, 공식 두 플레이어의 방 생성·참가와 두 패치판의 멀티 동기화는 아직 미검증이다.

최신 멀티 통합판은 현재 Wine 소유권 분류와 원시 목록 보존 경로를 연결해 새 독립 소스 검수를 통과했다(소스51개·C0 308개·추가 적대 조건45개, 보호82678항목 불변). 실제 두 플레이어의 방 생성·참가·동기화 합격은 아니다. G6 실행 감독기의 새 용량 감시에서도 전체 게임을 로그 용량으로 오인하는 계산과 기록 오류 때 자식 회수 누락 가능성을 찾아 새 복사본에서 수정 중이다. 후속 감독기 독립 검수에서도 시간 조회·대기 중 예외의 회수 누락과 중단 결과/실패 기록 오류가 추가로 확인돼 최소 수리 중이다. G6 새 물리 소스의 정확한 실행 전 검사72개·subtest15개는 별도로 통과했다. 후속 감독기 수리판은 독립 검사26개·계약 반례30개·실행 조건41개를 통과했다. 그러나 새 실행 시작 유효시간이 지났고 디스크 용량도 필수 기준보다 부족해 승인·게임 실행 전에 거부했다. 기존 증거를 보존한 채 새 RAM 실행 경로와 전체 파일 복원 검증을 준비 중이다. RAM 보관 도구는 독립 검사에서 메모리 계산 누락·복원 증거 정리·실패한 보관본의 성공 판정 오류가 나와 새 수리판을 준비 중이다. G6 RAM 준비본의 검사 입력 누락·경로 제한 오류를 고친 새 판은 독립 소스 검수를 통과했다(격리 실행 전 검사72개·subtest15개, 감독기32개·추가 독립 검사15개). 실제 게임 실행 승인은 아니다. RAM 보관 도구의 후속 수리판은 작업 검사32개를 통과했지만, 이전 동결 검증 산출물을 직접 import하며 Python 캐시를 생성해 보호 디렉터리 메타데이터가 바뀌었다. 이 보호 실패와 이전 기준은 그대로 보존한다. 새 복사본의 독립 검사32개·추가69개는 통과했지만, 완료 처리와 실패 기록 저장이 함께 실패하면 실패한 보관본을 성공으로 오인하는 반례가 나와 성공한 보관 호출에서만 반환하는 별도 확인값을 요구하도록 새 판을 만들었다(독립 검사36개·비교69개·새 검사20개 통과). 새 검사 보호7561항목에 추가 변화는 없었으나 과거 사고 FAIL과 전체 승인 보류는 유지한다. 모두 실제 게임 실행 전 소스 검증이며 제품·멀티 합격으로 확대하지 않는다.

후속 공식판 실행에서도 타이틀 메뉴·동일 프로세스30초 생존을 확인했다. 실행 중 보조 프로세스의 실제 소유권 확보는 확인했지만, 최종 프로세스 목록 조회 오류로 전체 정리는 UNKNOWN이다. 이를 완료나 멀티 성공으로 표시하지 않는다.
새 판의 입력 SHA·저장/로드·실행·멀티 검증 범위는 [2613 작업 계약](docs/history/20261010_esl2613_goal_contract.md)에 기록한다.

멀티 감독기의 생성 직후 핸들 보존 수리판은 정리 상태 `UNKNOWN` 기록 누락으로 한 차례 반려됐다(21개 중 19 통과·2 실패). 새 복사본에서 보강한 뒤 **독립 결함 주입 검사 41개와 격리한 파생 선택 검사 15개가 통과**했다. 이는 해당 소스 수리만의 수용이며 전체 27개 조합 검사의 새 통과나 실제 멀티 성공은 아니다. 검수에서 기록한 SHA·메타데이터 필드는 불변이지만 일부 수치 메타데이터의 실행 전 기록은 빠져 있어 전수 보존 증거로 확대하지 않는다. 실제 게임의 두 피어 접속·동기화 검증은 아직 미완료다.

사용자 재개·디스크 정리 후 새 전체 게임 사본과 fresh prefix 두 개에서 **공식 2613 두 PE를 실제 실행**했다. 양쪽의 IPX 등록은 성공했지만, 타이틀 전에 같은 `SetVideoMode()` 오류 대화상자가 발생했다(`local/runtime/20261010_actual2613_two_peer_control_retry/actual_control_result.json`). 기존 Wine 가상 데스크톱 설정으로 새 사본에서 재실행한 결과, 양쪽 모두 800×600 게임 창은 생성됐으나 60초 이상 검은 화면이었다(`local/runtime/20261010_actual2613_two_peer_desktop_retry/actual_control_result.json`). 인식 가능한 입력 대상이 없어 입력하지 않았고, 해당 두 prefix와 소유 X 프로세스는 종료·회수했다. **방 생성·참가·시작·동기화는 미검증이며, 멀티 결함으로 단정하지 않는다.**
통신 가드가 비소켓의 `ENOTSOCK`를 다른 오류로 바꿔 PulseAudio의 정상 `write` 대체 경로를 막는 결함을 확인했다. 네트워크 허용 범위를 바꾸지 않는 최소 오류 반환 수정은 독립 재빌드와 설치된 실제 `pa_write`의 32/64비트 old-fail/new-pass 검사로 수용됐다. 정확한 양 ABI 가드 경로로 실행한 새 공식판 두 피어는 모두 실제 타이틀에 도달했고, 초기 로그에서 기존 PulseAudio 오류가 발생하지 않았다. 후속 실제 IPX 선택 뒤에는 방 생성 연결 오류가 발생했고, native wsock32 우선 비교 실행도 방 생성·참가·시작까지 확인하지 못했다. **멀티 합격은 아니며, 최신 사용자 지시에 따라 해당 진단은 중단했다.** 새 싱글 실행은 성공했던 양 ABI 경로를 재사용한다. 과거 실패·실행 사본은 보존하며 RAM/차분 보관 도구 검수를 이 경로의 전제로 삼지 않는다.

[사용자 달성·종료 결정](docs/feedback/G2_G5_USER_COMPLETION_20261003.md)은 새 자동/멀티 검증 PASS를 뜻하지 않는다.
새 결함 보고나 명시적인 새 지시 없이 G2·G5를 자동 재개하지 않는다.

[G6·G7 분석·해결 방향](analysis/memory_maps/g6_g7_local_player_slot_bugs_20261004.md)

**G1이 현재 최우선이다.** 2026-10-06 사용자 결정으로 V2s gate는 W-1(Scale2x로 설명되지 않는 흑색 ≤2,000)을 쓰며,
save006 고정 장면·키/가장자리 스크롤 stale은 0~1 수준까지 수리됐다. 기존 QHD 시야 확장이나 800×600 최종 버퍼의 단순 2배 확대는
고해상도 스프라이트의 추가 디테일을 살리지 못하므로 G1 완성 경로가 아니다.

## 모델 역할

현재 선택은 Codex다(2026-10-09 사용자 전환). 역할별 provider를 바꿀 수 있으며 최신 선택은 [역할 계약](docs/MODEL_ROUTING.md)을 따른다.

- **큰 방향/상위 계획:** `astra/high` (큰 분기·교착에서만)
- **중간 계획/독립 컨펌:** `sol/high`
- **실무:** `luna/high`

`luna`/`sol`/`astra`는 모델 캐시의 계열별 최신으로 해석한다. 실무가 자기 결과를 최종 승인하지 않으며,
설정 실패 시 다른 모델로 자동 폴백하지 않는다.

## 개발과 제어

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
git config core.hooksPath .githooks
make doctor
make check
loop/loopctl.sh status
loop/loopctl.sh models      # 모델 설정 조회만; 실행하지 않음
```

현재 머신에는 기존 패키지를 재사용하는venv를 세팅했다. 실제 모델 세션/서비스는 켜지 않았다.
초기 안전 pin은 세팅에서 수행한다. 새 복제 환경에서는 원본/profile을 검토한 뒤
`checks/safety.sh pin`으로 한 번 고정한다. 자동 재pin은 금지다.
실제 실행 설정은 [loop/README.md](loop/README.md). 기본 비활성/최대1바퀴/자동커밋 없음이다.
서비스 이름은 **syw2plus-patch-loop.service**로 기존 루프와 충돌하지 않는다.

`loop/FULL_TEST` 요청은 세션 밖에서`tests/test_build.sh`→`make check`를 실행한다.
이 결과는Fast이지 원본 앱/8인/16인/24k/144k를 실제로 돌린 결과가 아니다.

## 기존 패치와 로컬 입력

- [전비 패치/원복](patches/population/README.md), [과거QHD 참고](patches/resolution/README.md).

- 출처에 없는 라이선스를 임의 부여하지 않았다.
