## 1. 결론 먼저

**AI 생산 결정 경로에는 자원을 보는 게이트가 하나도 없다.** 8개 게이트 전부가
**상태·구성(composition)·밀집도·케이던스** 기반이다. 따라서 "자원이 96.8% 남았는데 멈춘다"는
관측은 이상 현상이 아니라 **이 경로의 정상 동작**이다. N81이 자원을 배제한 것은 옳았고,
배제 뒤에 남는 후보는 아래 G-1~G-8이다.

정지를 **영구화**할 수 있는 게이트는 그 중 셋이며, 셋 다 **유닛 구성이 고정되면 같이 고정**된다:

| 후보 | 게이트 | 왜 영구화되나 |
|---|---|---|
| **H-RATIO** | `FUN_0043E7F0` 비율 상한 (`type_spec+0x32`) | 타입별 보유 비율이 상한을 넘으면 그 타입 영구 거부. 구성이 안 변하면 해소 없음 |
| **H-TYPEMAX** | `FUN_0043E7F0` 타입별 개수 상한 (`type_spec+0x34` 또는 시나리오 override) | 상동 |
| **H-CROWD** | `FUN_00406B00` 11×11 동종·동소유 밀집 ≥7 | 유닛이 안 죽고 안 움직이면 해소 없음 |

lap500 N146은 **144k tick 동안 소실 14기뿐**임을 수치로 재확인했다 — 즉 이 fixture에서
구성은 사실상 **동결**돼 있다. 세 게이트 전부 "구성이 동결되면 영구"라는 성질을 공유하므로,

## 2. 진입점 `FUN_00406770` @ `0x00406770` — per-unit AI dispatch

`__fastcall(ecx = UnitStruct*)`. 원본 바이트 확인.

```
00406774  cmp dword ptr [esi+0x1f4], 0x64   ; G-1 유닛 상태 == 100 아니면 return 0
0040677b  je  0x406782
00406782  mov ecx, [0x8924b8]               ; 전역 tick
00406788  cmp ecx, 0x32                     ; G-2 tick >= 50 아니면 return 0
00406792  shr ecx, 1                        ; half = tick>>1
00406794  test cl, 1
00406797  jne 0x4067ee                      ; half 홀수 -> 연구(ODD) 분기
; ---- EVEN 분기 = 생산/건설 ----
00406799  test dword ptr [esi+0x1d8], 0x80000  ; G-3 auto-respond 플래그
004067a5  ...  div 10 ; test edx,edx        ; G-4 half % 10 == 0
004067b6  call 0x406b00                     ; -> FUN_00406B00 (생산)
```

- **G-1** `UnitStruct+0x1F4 == 100` — 디스패치 대상 유닛(생산 건물)의 상태.
- **G-2** 전역 tick `DAT_008924B8 >= 0x32`.
- **G-3** `UnitStruct+0x1D8 & 0x80000` — "auto-respond" 능력 플래그.
- **G-4** 케이던스: `(tick>>1)` 짝수 **그리고** `(tick>>1) % 10 == 0` ⇒ **20 tick마다 1회**.

ODD 분기(=연구)는 별도 게이트를 갖는다(참고용, 생산 아님):
per-owner AI 활성 바이트 `0x00956772 + owner*0x3ABC`, `DAT_008924C8 % 0x14 == 0`,
LCG 추첨 `%100 < 0x14`(20%), 그리고 **per-owner 1000 tick 쿨다운**
`|DAT_00959A88[owner*0x3ABC] - tick| > 1000`. 이 쿨다운은 **재장전되므로 영구 정지 후보가 아니다.**

## 4. `FUN_0043E7F0` @ `0x0043E7F0` — 생산 유효성 (G-6), **가장 유력한 정지 원인**

`__thiscall(ecx = 컨트롤러, stack = kind)`. 타입 스펙 스트라이드는 바이트로 확인한
`lea` 사슬(9→19→57→229, `shl 2`)이 정확히 **916 = 0x394**다. 레코드 베이스 `0x009B5228`
기준 필드: `+0x24` 플래그(`0x9B524C`) · `+0x28` 진영(`0x9B5250`) · `+0x32` 비율상한(`0x9B525A`)
· `+0x34` 개수상한(`0x9B525C`).

거부(=`return 0`) 조건 5가지, 원본 바이트 순서대로:

1. **영웅 진영 불일치** — `flags & 8`일 때 `type_spec+0x28 != ctrl[0]`(진영).
2. **영웅 사망 쿨다운** — `flags & 8`일 때 `ctrl + 0x4D0 + kind*2 > 0`.
   (참고 저장소는 이 자리를 "이미 보유"로 오독했다가 **사망 재등용 카운트다운**으로 정정했다.)
3. **H-TYPEMAX — 타입별 개수 상한**
   ```
   0043e887  mov di, word ptr [esi*2 + 0x89a388]   ; cur = count[kind + owner*200]
   0043e88f  cmp di, bp                            ; bp = 타입 상한
   0043e892  jl  통과                              ; cur >= 상한이면 거부
   ```
   상한 `bp`는 `DAT_009E1DD8 == 0`이면 `type_spec+0x34`(`0x9B525C`), 아니면 **시나리오 override**
   `0x00B3DE70 + (kind + owner*0x19C)*2`.
   보유 개수는 `0x0089A388 + (kind + owner*200)*2` — **per-owner per-type 개수 표(short, 200 타입)**.
4. **타입 가용 플래그 0** — `0x00B3E000 + (kind + owner*0x19C)*2 == 0`이면 거부.
   `0xB3E000 - 0xB3DE70 = 0x190 = 200 short` ⇒ 한 owner 행(412 short) 안에
   **[0..199]=타입 상한 override, [200..399]=타입 가용 플래그, [400..411]=여분** 구조다.
5. **H-RATIO — 비율 상한**
   ```
   0043e8c1  mov dx, word ptr [ecx+0x200a]  ; total = owner 총 유닛 수 (short)
   0043e8c8  test dx,dx / jne               ; 0이면 비율 0으로 통과
   0043e8e1  idiv esi                       ; eax = cur*100 / total  (백분율)
   0043e8e3  cmp ax, [esp+0x14]             ; = type_spec+0x32 비율 상한
   0043e8e8  jle 통과                       ; **백분율 > 상한이면 거부**
   ```
   참고 저장소가 `ai_production_ratio_cap`으로 부르는 필드가 **바로 이 `+0x32`**이며,
   분포는 **sentinel 0 · 농부 60 · 나머지 30**으로 표기돼 있다(미검증, §6).
6. 추가로 `flags & 8`(영웅)이면 `ctrl + 0x980 >= 5`일 때 거부 — **영웅 5기 상한**.

> **핵심:** 3·5는 `cur`(보유 개수)와 `total`(총 유닛 수)만 본다. **자원은 보지 않는다.**
> 구성이 고정되면 판정도 고정되고, 그 kind는 **영구히** 거부된다.

## 5. 생산 후보표 `DAT_004EC514` — 유일하게 파일에 있는 표

`0x4EC514` rva `0xEC514`는 `.data` raw 범위(`0xEC000`+`0xD000`) **안**이라 원본 파일에서
직접 읽었다. 순회 종료는 143 고정 카운트가 아니라 **sentinel**이다 —
`FUN_00406C70`은 `eax += 0x12` 후 `cmp word [eax-4], -2`, 즉 **다음 레코드의 `+0x00` flag가
`0xFFFE`**이면 멈춘다(이 문서 초판 검사는 종료 워드를 `+0x0E`로 잘못 잡아 365건을 읽었고,
바이트로 정정해 143건을 얻었다).

실측: **143 엔트리 = 생산 65 + 연구 78**, flag 워드는 143건 전부 `0x000F`
(4-bit 진영 마스크: 조선1·일본2·명4·기타8). 참고 저장소 문서의 "143 = 연구78 + 생산65"와
**독립 일치**한다.

**생산 가능 건물은 27종이고, 건물 1종이 만들 수 있는 kind는 최대 4종이다:**

| 건물당 생산 kind 수 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 건물 종 수 | 5 | 10 | 8 | 4 |

이것이 H-RATIO/H-TYPEMAX/H-CROWD를 **정량적으로 강하게** 만든다 — 한 건물을 완전히 벙어리로
만드는 데 필요한 것은 **최대 4개 kind**가 동시에 거부되는 것뿐이고, 5종 건물은 **kind 1개**만
막히면 영구히 아무것도 못 만든다.

**반대로 정적으로 가릴 수 없는 것:** G-6이 읽는 표(`0x9B5228` 타입 스펙, `0x89A388` 개수,
`0xB3DE70`/`0xB3E000` 시나리오, `0x956770` 컨트롤러)와 G-7의 유닛 풀(`0x66B790`)은 전부
rva `0xF9000` **바깥**이라 **파일에 초기값이 없다**(런타임/데이터 파일에서 채워진다).
따라서 비율 상한 실제 값, 타입별 상한, 어떤 kind가 `0x4|0x400` 플래그를 갖는지는
**런타임에서 읽어야 한다.** 이 문서는 그것을 추정하지 않는다.

## 6. 참고 저장소와의 대조 (읽기 전용)

`Syw2plus_re`의 Ghidra 산출물(`analysis/ghidra_output/FUN_00406770.c`, `FUN_00406b00.c`,
`FUN_00406c70.c`, `FUN_0043e7f0.c`)은 위 디스어셈블과 **구조가 일치**한다. 다만:

- 참고 저장소 `analysis/memory_maps/ai_production_table.md`는 `FUN_00406770 → FUN_00406C70(1)`을
  **"연구 진로"**, `FUN_00406B00 → FUN_00406C70(0)`을 **"생산 진로"**라고 적은 줄과,
  같은 문서 앞부분의 "`FUN_00406c70(0)` = 생산용" 표기가 있는데 **후자가 맞다** —
  `param_2 == 0`이 `produce_kind != -1 && research_kind == -1`을 고르고 `+0x04`(produce_kind)를
  반환한다. 바이트로 확인했다.
- `decomp/cleaned/ai_strategy.c`는 **재현 구현 전용**이며 파일 스스로 "바이너리 미발견"으로
  표시한다. **원본 AI 생산 로직의 근거로 쓰면 안 된다.** 이 문서는 쓰지 않았다.
- 참고 저장소 `bprod_loop_is_owner1_only_0822.md`의 "owner1 전용"은 **참고 저장소 재현 엔진
  (`plan_c/tick_scheduler.cpp`)의 결함**이며, 같은 문서가 "원본 `FUN_00406B00`에는 소유자
  게이트가 없다"고 명시한다. 위 디스어셈블도 그렇다(G-5는 owner별 **활성 바이트**이지
  owner 고정이 아니다). **이 결함을 원본/후보 쪽으로 옮겨 오면 안 된다.**
- `ai_production_ratio_cap` 분포(농부60·나머지30)는 참고 저장소 `unit_type_specs.h` 주석이
  출처이며 **이 lap이 검증하지 않았다.** 값은 §7 probe로 확인한다.

## 7. 판별용 읽기 전용 런타임 probe 설계 (work tier 인계, AI 변경 없음)

세 후보를 **한 번의 관측**으로 가른다. 전부 **메모리 읽기만** 하므로 (ㄴ) 승인 대상이 아니다.

정지한 owner(예: owner5, tick14,641 전후)에 대해 매 표본 다음을 읽는다:

1. `0x00956772 + owner*0x3ABC` (AI 활성 바이트) — **0이면 H-AIOFF 확정**, 나머지 전부 기각.
2. `0x0089A388 + (kind + owner*200)*2` 전 kind — 보유 개수 벡터.
3. `ctrl + 0x200A` — owner 총 유닛 수.
4. `0x009B5228 + kind*0x394`의 `+0x24`(플래그) `+0x32`(비율상한) `+0x34`(개수상한) 전 kind.
   (상수이므로 1회만 읽으면 된다.)
5. `0x009E1DD8`, 그리고 0이 아니면 `0x00B3DE70`/`0x00B3E000 + (kind + owner*0x19C)*2`.
6. 그 owner의 생산 건물마다 `UnitStruct+0x1F4`(상태) · `+0x1D8 & 0x80000` · 타일 `+0x2A2/+0x2A4`.

**사전 고정 판정식(데이터 개봉 전에 확정할 것):** 그 owner의 생산 건물이 만들 수 있는
(건물, kind) 쌍 전체를 `DAT_004EC514` 65개 생산행으로 열거하고, 각 쌍에 대해

- `cur >= typemax` → **H-TYPEMAX**
- `cur*100/total > ratio_cap` → **H-RATIO**
- 가용 플래그 0 → **H-AVAIL**
- 위 셋 다 통과인데 11×11 동종·동소유 계수 >= 7 → **H-CROWD**
- 전부 통과인데도 발주가 없다 → **H-STATE**(G-1 상태 100 또는 G-3 플래그 문제) 또는 미지

로 분류한다. **정지 tick에서 모든 쌍이 어떤 이유로든 거부로 분류되면 원인 특정**이고,
거부되지 않는 쌍이 남으면 **위 6 게이트 밖에 원인이 있다**는 뜻이므로 그대로 보고한다.

**주의(필수):** lap500 N144가 확정한 대로 이 fixture는 **결정적**이다. 같은 조건 재실행은
새 정보를 주지 않으므로, 이 probe는 **새 run이 아니라 기존 계보와 같은 궤적 위에서** 읽거나
관측 채널만 추가해 1회 실행한다. 또한 lap410 정정2대로 **배포 진단 DLL의 `0x008990C8`·1200

## 8. G2 / F4(B)에 대한 부수 발견 (구현 착수 아님, 범위 입력용)

- **F4(B) 32-bit 확장 범위 입력:** 이 경로에서만 16-bit 필드가 3곳 더 나온다 —
  `0x0089A388` per-owner per-type 개수(short) · `ctrl + 0x200A` 총 유닛 수(short) ·
  `0x00B3DE70`/`0x00B3E000` 시나리오 표(short). F4(B) 범위 산정 시 전비 장부 5 사이트 외에
  **이 3곳도 함께 세어야** 한다. 이 lap은 어느 것도 **변경하지 않았다.**
- **G2 자연 도달(W23 A1 `NOT_FEASIBLE`)에 코드 수준 설명이 생겼다.** 비율 상한이 실제로
  "농부60·나머지30"이라면, AI는 **어떤 비농부 타입도 전체의 30%를 넘게 보유할 수 없다.**
  생산 가능 kind가 건물당 최대 4종뿐인 것과 겹치면, AI 자력으로 도달 가능한 군대 규모·구성에는
  **구조적 상한**이 있다. 이는 W23 A1의 측정 결과와 **정합**하지만, 비율 상한 실제 값이
  미검증이므로 **아직 증명이 아니다** — §7 probe 4번이 그 값을 확정한다.
- **G-7의 `0x66B790` 직접 인덱싱은 풀 재배치 fixup 대상이다.** `g2_capacity_boundaries.md`가
  센 베이스 참조 115건 중 하나이며, 재배치 후보에서 이 상수가 고쳐지지 않으면
  **AI 밀집 검사가 엉뚱한 메모리를 읽는다.** 후보 검증 시 확인 항목으로 둔다.
