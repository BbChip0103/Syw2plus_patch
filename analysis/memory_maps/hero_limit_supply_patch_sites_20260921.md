## 전비 상한 공식과 그 사이트

```
supply_limit(PlayerStruct +0x2012) = 기본치 + 장수당증가 × 살아있는 장수 수
```

| VA | 원본 명령 | 역할 |
|---|---|---|
| `0043FDD6` | `push ebx/ebp/esi/edi` | 전비 계산 함수 진입 |
| `0043FDE3` | `mov [esp+0x18], eax`(eax=0) | 누적기 0 초기화 |
| `0043FDE7` | `mov [ebp+0x980], eax` | 장수 수 0 초기화 |
| `0043FDDE` | `mov edi, 0x9B53D0` | 유닛 템플릿 순회 시작 (= `0x9B524C + 0x184`) |
| `0043FE00` | `test byte [edi-0x184], 8` | 템플릿 flags `&8` = 장수만 통과 |
| **`0043FE9E`** | `add ecx, 0xC8` | **장수당 전비 200** |
| `0043FEA9` | `mov [ebp+0x980], eax` | 장수 수 증가 |
| **`0043FFD4`** | `add eax, 0x5DC` | **기본 전비 1500** |
| `0043FFD9` | `mov word [ebp+0x2012], ax` | supply_limit 기록 |

**`+0x2012`에 쓰는 명령은 `0043FFD9` 하나뿐이다.** 전수 스캔에서 나머지 3곳
(`0043EE03`, `0043F0F3`, `0043F43F`)은 모두 `movsx` 읽기다. 별도 최대치 클램프 상수는
`.text 0x43E000~0x441000`에서 `0x9C4`(2500)·`0xBB8`(3000) 모두 **0건**이다.
⇒ 최대 전비는 `기본치 + 장수당 × 장수상한`으로 **파생**되며 독립 상한이 없다.

`add eax,0x5DC`·`add ecx,0xC8` 형태도 각각 해당 1곳뿐이다(다른 `0x5DC` 히트는 전부
`push`/`cmp`이거나 정렬 오차). 이는 [[supply-limit-hero-formula-runtime-confirmed-0906]]의
`1500 + 200×장수` 공식을 정적으로 재확인한다.

## 장수 상한 비교 사이트 — **5곳**

장수 수는 PlayerStruct `+0x980`이다. PlayerStruct[0] 베이스 `0x956770` + `0x980` = **`0x9570F0`**
이므로, 같은 필드가 두 가지 주소 형태로 나타난다.

| VA | 원본 명령 | 분기 | 직전 장수 플래그 테스트 |
|---|---|---|---|
| `0040D8D3` | `cmp dword [ecx*4+0x9570F0], 5` | `jge` → 생산 불가 | `0040D8B3 test [ebp+0x9B524C], 8` |
| `004121A8` | `cmp dword [ecx*4+0x9570F0], 5` | `jl` → 계속 | `0041218A test [edx*4+0x9B524C], 8` |
| `004124D2` | `cmp dword [ecx*4+0x9570F0], 5` | `jl` → 계속 | `004124B8 test [edx*4+0x9B524C], 8` |
| `0049A5C3` | `cmp dword [eax*4+0x9570F0], 5` | `jl` → 계속 | `0049A596 test cl, 8` |
| **`0043E8F7`** | `cmp dword [ecx+0x980], 5` | `jl` → `return 1`, 아니면 `return 0` | `0043E84A and ebx, 8` |

**5곳 전부가 바로 앞에 템플릿 flags `&8` 테스트를 달고 있다.** 전수 근거:

- `0x9570F0` 리터럴 `.text` 전수 = **4건**, 전부 위 `cmp ...,5`.
- `+0x980` disp32 전수 = 7건 중 상한 비교는 `0043E8F7` **1건**, 나머지는 전비 함수의
  초기화/증가/읽기 4건과 다른 구조체로 보이는 2건(`004C38ED`, `004C4BDE`가 `0x34BC` 기록).

### 장수 플래그 = 템플릿 `+0x24` bit3

`0043E7F0` 함수에서 `esi = type × 0x394`(lea 체인 검산: 9→19→57→229, `<<2` = 916)이고
`[esi+0x9B524C]`는 유닛 템플릿 레코드 `+0x24`다. 원본 런타임 캡처
`unit_templates_9b5228_394x152.raw`에서 `+0x24 & 8`인 type은 **76~102 (23종)** 이며,
이 구간은 비용표 `+0x10`이 **전비 0**인 구간과 정확히 겹친다. 장수는 전비를 소모하지
않고 상한을 올려주므로 정합적이고, 참고 저장소 `Syw2plus_re/analysis/memory_maps/hero_kind_confirmed.md`의 명명 범위
(`0x4D` 이순신 ~ `0x66`)와도 일치한다.

⚠ 참고 저장소 `plan_c`의 "type 40~59 = 장수 20인" 표기는 이 바이너리의 type 인덱스와
다른 공간이다. 이 문서의 76~102가 `.text`가 실제로 쓰는 값이다.

## 커뮤니티 패치본 diff (독립 확인)

`ESL 2501` 기준 바이트 diff. 둘 다 PE 헤더 2곳(Characteristics `0x010F→0x012F`, 체크섬) 제외.

| 대상 | 장수 4사이트 | `0043E8F7` | `0043FE9E` 장수당 | `0043FFD4` 기본 | 결과 |
|---|---|---|---|---|---|
| 2503 장수7명+최대2600 | `05→07` | **미변경(5)** | `200→100` | `1500→1900` | 1900+100×7 = 2600 |
| 2503 장수제한해제+기본2500 | `05→0A` | **미변경(5)** | `200→0` | `1500→2500` | 2500 고정, 상한 10 |

각각 **11바이트**(기능 9바이트) 차이뿐이다. `2501 → 2503(장수7명)` diff가
`[ESL]Syw2plus 2601 ↔ 2503` diff(29바이트)에서 버전 차이 20바이트를 분리해 준다.

**두 커뮤니티 패치 모두 `0043E8F7`을 5로 남겼다.** 해석은 미결이다:
(a) 두 제작자가 같은 이유로 누락했거나, (b) 이 경로가 실제 생산 판정에 도달하지 않는다.
"장수제한해제"가 상한을 10으로 올렸는데도 배포·사용된 점은 (b) 쪽 방증이지만
확정 근거는 아니다. **실행 검증 필요.**

## 이번 세션 생성물

`260921_temp/[ESL]Syw2plus 2601_장수7명_전비1600-200-3000.exe`
(SHA-256 `70685e4654a919a575ae36fa7382ba3a04ef6f3a234e104db96fc83ade36e4b6`).
장수 5사이트 `05→07`, `0043FFD4` `1500→1600`, `0043FE9E`는 이미 200이라 무변경.
⇒ `1600 + 200×7 = 3000`. 변경 7바이트, 원본 무변경 확인. **게임 실행 미검증.**
저장소 밖 임시 경로 생성물이며 커밋 대상이 아니다.

## HQCDD 16:9와의 비충돌 여부

패치 7바이트는 **전부 `.text`** 다. HQCDD v0.7.1은 `.text`/`.rdata`/초기 `.data`의
SHA-256을 검증하므로 이 EXE에서는 16:9 요청이 거부된다(다른 출력 기능은 무관하게 동작).
공존하려면 `.text` 대신 런타임 메모리에서 장수/전비를 바꾸는 방식이 필요하다.
상세는 [[hqcdd-external-display-map-20260921]].
