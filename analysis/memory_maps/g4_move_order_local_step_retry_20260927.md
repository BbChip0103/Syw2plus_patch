## 1. Unit 명령 상태 디스패처 → MOVE 상태 핸들러 (exact call chain)

기존 진단 계약(`docs/history/laps/20260916_g4_original_order_issuer_probe.md`)이 확정한
`Unit+0x290`=현재 명령 상태(1=대기,3=이동,4=공격)를 시작점으로, per-tick 메인 디스패처
`FUN_0048DDD0`을 역추적했다.

- `0x48DDD0` 안 `0x48E3F4`: `movsx eax,WORD[esi+0x290]`; `lea ecx,[eax-1]`; `cmp ecx,0x56`;
  `ja 0x48EA15`(기본 핸들러) — 상태값 1..0x57 범위를 전제한다.
- byte 표(state-1 인덱스 → jump-table 인덱스) 파일 오프셋 `0x8EB30`(52항목+기본52), jump
  table 파일 오프셋 `0x8EA5C`(DWORD×53, VA `0x48EA5C`).
- **state=3(이동)** → `ecx=2` → 표 `byte[2]=2` → jump table entry `[2]=0x48E6FD`.
- `0x48E6FD`: `call 0x48C3E0`(공용 진입 helper, 다른 모든 상태도 호출); `call 0x40C390`
  (**이동 전용, 아래 §2**); `call 0x48BD10`; `jmp 0x48EA45`(공용 반환).
- **정적 xref 전수 확인**: `.text` 전체에서 `call 0x40c390`은 이 한 곳(`0x48E706`)뿐이다
  (grep 결과 1건). 즉 `0x40C390` 내부 상수는 오직 플레이어/AI가 발행한 **MOVE 주문의 매틱
  스텝 처리**에만 쓰인다 — 공격(state=4, jump table `[3]=0x48E815`)이나 다른 상태와 코드
  경로를 공유하지 않는다.

## 2. `FUN_0040C390`(이동 스텝 진입) → `FUN_0040B7E0`/`FUN_0040B810`(로컬 스텝/재시도)

`0x0040C390`(파일 오프셋 `0xC390`):

```
push esi
push 0x0
mov  esi,ecx
push 0x4          ; <-- 파일 오프셋 0xC395, 바이트 `6a 04`
call 0x40B7E0
cmp  eax,0x1
jne  0x40C3B1
...
```

`ecx`(unit)는 그대로 두고 `push 0,4; call 0x40B7E0(unit, 4, 0)`로 넘어간다. `0x40B7E0`은
`Unit+0x1D8 & 0x10` 플래그로 `0x40C050`(비행/특수 이동형, 미조사) 또는 `0x40B810`(지상형,
아래)로 그대로 인자를 전달하는 얇은 디스패처다. `0x40B7E0`은 `.text` 전체에서 **30곳**에서
호출된다(다른 유닛 서브시스템이 각자 다른 "mode" 정수를 넘긴다 — 예: 애니메이션/전투 갱신 등,
전수 xref 확인함). **그러나 `mode=4`를 넘기는 호출은 이 `0x40C390`(=이동 상태 핸들러) 한
곳뿐이다.** 즉 `mode` 값은 여러 서브시스템이 공유하는 dispatcher의 "어떤 목적으로 부르는지"
태그이며, 값 자체(`4`)의 재사용 여부는 상관없이 이 특정 호출 지점만 패치 대상이 된다.

`0x40B810`(지상 이동 스텝 함수, `mode`/`value` 그대로 전달):

- `Unit+0x1D8 & 1` 이면 조기 반환(비이동형 서브타입).
- `Unit+0x1C==1`이면 회전/애니메이션 서브상태 머신(`0x40C3F0`, 방향 전환 대기 — 경로탐색과
  무관, 애니메이션 프레임 개수 테이블 인덱싱만 함)으로 위임.
- 그 외 정상 이동 스텝 처리(파일 오프셋 `0x8930`~`0x8B71` 부근, VA `0x40B930`~`0x40BB71`):
  1. 목표 좌표가 이미 일치하고(`Unit+0x2A2/0x2A4` == 캐시된 `Unit+0x678/0x67A`)
     `Unit+0x692==0`이면 실제 스텝 계산 함수 `call 0x41AF90`(§3, bounding-box 제한 라인/경로
     탐색 진입점)을 부른다. 반환값이 `-1`(경로 스텝 없음/막힘)이면 아래 4번 "로컬 재시도" 분기로
     떨어진다(`jmp 0x40BA01`).
  2. 그렇지 않으면(`0x40BA62`) 목표 대비 현재 위치의 부호로 `dx,dy ∈ {-1,0,+1}` 후보 한 스텝을
     계산(`Unit+0x674/0x676`)하고 `call 0x412A70`(타일 통행 가능 검사, 인자 `dx,dy,방향비트`)로
     그 한 스텝이 유효한지 검사한다.
  3. 유효하면(§case, `0x40BAF8`~) 그 스텝을 커밋하고 시도횟수 `Unit+0x682`를 증가시키며
     **파일 오프셋 `0x3EB2F`(VA `0x40BB43..0x40BB4A`)에서 재시도 쿨다운 `Unit+0x680`을 상수
     `5`로 리셋**한다. `Unit+0x682`(누적 시도 횟수)를 스택 값 `[esp+0x20]`과 비교하는데, 이
     스택 슬롯은 함수 진입 시 원래 `mode` 인자 위치(§2 상단 `4`)와 정확히 일치한다 — 즉
     **`mode` 인자 값(4)이 이중으로 "로컬 스텝 재시도 최대 횟수" 임계값 역할을 한다.**
     `시도횟수 < 4`면 그대로 반환하고, `시도횟수 >= 4`면 `call 0x40B740(targetX,targetY)`로
     떨어진다.
  4. 스텝이 무효하거나(§2) 목표가 바뀌었으면(`0x40BA01`) 같은 카운터/쿨다운 로직을 다시 거친다
     (파일 오프셋 `0x3EA2F`, VA `0x40BA28..0x40BA2F`도 같은 `Unit+0x680=5` 리셋).
- `FUN_0040B740(targetX,targetY)`: 실제 A*류 그래프 탐색이 아니라, 목표 좌표를 맵 경계로
  클램프하고(전역 맵 크기 `0xB3DE34`/`0xB3DE36`) `Unit+0x2B0/0x2B2`(원거리 목표), `Unit+0x67C/
  0x67E=-1`(캐시 무효화), `Unit+0x680/0x682/0x634=0`(재시도 카운터 리셋)만 하는 **"로컬 탐색
  포기 후 원거리 목표로 재시도" 리셋 함수**다. 새 경로를 계산하지 않는다 — 이것이 §3의
  bounding-box 탐색이 실패했을 때 로컬 nudge를 4회까지 반복하다가 리셋을 반복하는 구조이며,
  장애물 앞에서 왕복/저효율 경로(`path_ratio_max`)가 생기는 원인으로 보인다(가설, §4).

## 3. `FUN_0041AF90` — 진짜 경로 스텝 진입점(라인/영역 제한, 이번 조사 범위 밖)

`0x41AF90`은 전역 카운터 `0x892FF8`이 `0x1770`(6000)을 넘으면 즉시 실패(`-1`) 반환하는
per-tick 전역 스로틀을 갖고 있고, 시작/목표 좌표를 각각 **`±0x1E`(30타일) 마진**으로 클램프한
bounding box를 만들어(맵 경계로 추가 클램프) 폴리모픽 오브젝트(`[Unit(?)+0]`의 vtable
`+4`, 인자 `(bp,di,...,0x892ff8,0x78,0x8,0x2)`)를 호출한다. `0x41B040` 부근은 Bresenham류
직선 스테핑(오차 누적, `sar eax,1`)으로 **시야선(line-of-sight) 검사**로 보이며, 진짜 격자
탐색(A*/flow-field) 본체는 vtable 호출 안쪽(별도 객체)에 있어 이번 조사에서는 진입점 인자만
확인했다. `0x1E`(30타일) 마진과 `0x78`(120)/`0x8`/`0x2` 인자의 의미, 그리고 vtable 안쪽 탐색
본체는 **미조사(범위 밖, 다음 조사 후보)**다.

## 5. 가설과 한계 (구현 전 명시)

- **가설**: 장애물 회피 시 로컬 4-방향 nudge를 4회만 시도하고 실패하면 §2 `0x40B740`으로
  "원거리 목표 재시도"만 반복하는 구조이므로, 로컬 재시도 횟수를 늘리면(4→8) 8타일 폭
  장애물(lap707 `obstacle_row`) 앞에서 왕복 리셋 대신 옆으로 더 밀어붙여 벗어날 확률이
  올라가 `path_ratio_max`가 낮아질 수 있다.
- **반대 가설(반증 가능)**: 로컬 nudge는 진짜 경로탐색이 아니라 단순 방향 밀기이므로, 횟수를
  늘려도 같은 막힌 방향만 더 오래 반복해 개선이 없거나(정체 유닛 수 증가) 오히려
  `arrival_tick`이 늘어날 수 있다. 이 경우 §3(0x41AF90 vtable 내부, 0x1E 마진)이 진짜
  개선 지점이라는 **대안 가설**로 다음 회차가 넘어가야 한다.
- 이 문서는 §3 vtable 내부 탐색 본체나 `Unit+0x680=5` 공유 쿨다운의 의미를 확정하지 않는다.
  코드경로 하나(§1의 `0x48e706` 유일 호출자)와 상수 위치(§4)만 exact-byte로 확정했다.

worst-case 유닛의 실제 경로가 후보에서 원본과 완전히 동일했다는 것은, 그 유닛이애초에 로컬
4방향 nudge 재시도 한도(§2-3)에 도달하지도 않았거나, 도달해도 8회까지 늘려도 같은 막다른
방향만 반복해 결과가 달라지지 않았음을 뜻한다 — §5에 미리 적어 둔 "반대 가설"과 일치한다.
도착률 하락(1기)은 이 패치가 무해하지 않다는 방향의 raw 신호이며(원인 미확정 — 재시도 예산
증가가 다른 유닛의 타이밍을 밀어냈을 가능성), 추가 조사 없이 이 패치를 채택 후보로 올리지
않는다.

**다음 가설(§3로 이관):** `FUN_0041AF90`의 bounding-box 마진(`0x1E`=30타일)과 그 안 vtable
탐색 본체가 미조사 상태다. 로컬 nudge가 아니라 이 진짜 탐색 진입점의 파라미터/본체가
`path_ratio_max`를 실제로 좌우할 가능성이 높다 — 다음 work가 vtable 호출 대상 객체를 특정하고
탐색 본체 내부의 노드/스텝 예산을 찾아야 한다. 이번 v1 바이트 패치(§4)는 되돌리지 않고
보존한다(반증 근거 자체가 재현 가능한 산출물).

## 7. `FUN_0041AF90` vtable 대상 특정 + 후보 v2 (lap709) — 가설 반증

STATUS 2026-09-27 08:55 지시가 넘긴 §3(vtable 호출 대상 미특정)을 이어서 조사했다. 원본
`[HQ]Syw2plus 2002.exe`(SHA `b56986e0…`)를 `objdump -Mintel -D`로 `.text` 전체 재덤프해
사람이 직접 오퍼랜드를 추적했다(Ghidra 미사용, 이전 lap들과 동일 방법).

### 7.1 전역 싱글턴 경로탐색 엔진 객체와 vtable

- `FUN_0041AF90`에서 bounding box를 채운 뒤 부르는 `call DWORD PTR [eax+0x4]`의 `ecx`("this")는
  `.text` 전수 xref로 유일 호출자인 `0x40b95d`(`FUN_0040B810`의 지상 이동 스텝 처리 안,
  §2의 caller)에서 `mov ecx, DWORD PTR ds:0xb92cbc`로 읽는 **전역 포인터**임을 확인했다(이
  값이 유일하게 쓰이는 xref, 다른 호출자 없음).
- `0xb92cbc`에 대한 쓰기 xref는 정확히 1곳(`0x424ca6`)뿐이다: `push 0x54; call 0x4da96e`
  (84바이트 `operator new`류 할당) → `push 0xc8; push 0xc8; mov ecx,eax; call 0x41ae70`
  (생성자, 인자 200,200 — 맵 그리드 치수로 추정) → 결과를 `mov ds:0xb92cbc,eax`로 저장.
  생성자 `FUN_0041AE70`은 멤버 초기화 호출(`0x46b6d0`) 뒤 `mov DWORD PTR [esi],0x4e57e0`로
  객체의 **vtable 포인터를 `0x4e57e0`(.rdata)로 고정**한다 — 이 엔진은 실행 중 단 한 번,
  게임 초기화 시 생성되는 싱글턴이며 다형(vtable 교체) 대상이 아니다(생성자 호출 xref도 1곳).
- `.rdata` 파일 오프셋 `0xe57e0`(=VA `0x4e57e0`)를 raw로 읽어 vtable 엔트리를 직접
  파싱했다: 엔트리[0]=`0x41ae90`(같은 클래스의 "footprint가 통행 가능 영역/기존 유닛과
  겹치는지" 정적 검사, 별도 호출 경로 — 이번 조사 범위 밖), **엔트리[1]=`0x46b840`**
  (`FUN_0041AF90`이 `[eax+4]`로 부르는 실제 대상, `eax=[ecx]=0x4e57e0`이므로 `[eax+4]`는
  vtable 두 번째 슬롯). 엔트리[2]=`0x421fe30`도 `.text` 범위 안이라 3번째 가상함수로
  보이나(미조사), 엔트리[3] 이후 값(`0x40a00000` 등)은 `.text`/`.rdata` 코드 범위 밖의
  부동소수점 상수로, vtable이 아니라 클래스 정적 데이터가 물리적으로 이어붙은 것으로 판단한다.

### 7.2 `FUN_0046B840` — 실제 그리드 탐색 본체 (윤곽만 확인, 완전 리버스는 범위 밖)

- 함수는 `sub esp,0x8` 프롤로그 뒤 다수의 컴파일러 재적재(같은 소스 값을 여러 스택 오프셋으로
  다시 읽는 패턴)로 좌표를 정리하고, 엔진 멤버 `+0x3c`(스텝 카운터, `mov WORD[esi+0x3c],ax`
  로 루프 진입 직전 0으로 초기화)를 두는 open-list 기반 탐색 루프(`0x46b912`~`0x46bac6`)를
  가진다. 각 반복은 이웃 확장 헬퍼 `FUN_0046BBF0`을 모드 인자(`0x8`=8방향, `0x4`=4방향— 이
  호출 인자가 §4의 "모드=4가 로컬 재시도 한도로 재사용됨"과는 무관한 별도 값)에 따라 최대
  8회 호출한다(`ret 0x28`, 첫 함수 경계로 확정, 이후 주소는 다른 함수).
  **한계(정직하게 기록):** 스텝 카운터(`WORD[esi+0x3c]`)와 비교되는 피연산자
  (`cmp ax, WORD PTR[esp+0x38]`)를 호출부 인자 9개(그 중 하나가 리터럴 `0x78`=120)에
  수기로 역산 대응시키려 했으나, 여러 좌표 인자가 콜사이트에서 같은 `[esp+0x34]` 표현식을
  세 번 재적재하는 컴파일러 패턴 때문에 스택 슬롯 산수가 두 가지 서로 다른 계산에서 일치하지
  않았다(사람이 손으로 짚은 오프셋 산수가 신뢰 구간을 벗어남). 따라서 **"`0x78`(120)이
  per-call 탐색 스텝 예산이다"는 가설은 미확정(과다 확신 금지)** — 이걸 정적으로만 더
  좁히려면 gdb 런타임 확인이 필요하나 이번 lap 범위로 넘기지 않는다(§7.4 다음 한 가지).

### 7.3 후보 v2 (채택) — bounding-box 마진 배증

- §4와 달리 마진 `0x1E`(30타일)는 애매함 없이 **4개의 exact byte** 위치로 완전히
  확정된다(두 좌표 각각 min/max 클램프, `lea esi,[eax-0x1e]`+`add eax,0x1e` 쌍 2벌,
  `.text` 전수 xref로 `FUN_0041AF90` 유일 호출자 확인 — §7.1). v2는 이 4곳만
  30→60타일(`0x1e`→`0x3c`, disp8 `0xe2`→`0xc4`)로 넓혀 bounding box를 121×121타일로
  키운다(`patches/pathing/g4_search_margin_budget_v2.py`, 파일 오프셋 `0x1AFC1/0x1AFCB/
  0x1AFED/0x1AFF6`). 7 tests 전부 PASS(원본 바이트 대조 포함).
- **반대 가설(사전 명시)**: obstacle_row 장애물은 8타일 폭으로, 원본 30타일 마진 안에도
  이미 충분히 들어온다 — 이 경우 마진을 넓혀도 실제 탐색 행동이 달라지지 않아 개선이
  없을 것으로 예상했다.
